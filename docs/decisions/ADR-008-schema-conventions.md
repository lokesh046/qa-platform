# ADR-008: Schema conventions — keys, enums, timestamps, constraint names

Date: 2026-11-08
Status: Accepted

## Context

Step 5 writes the first migration. Every convention chosen here is applied
five times immediately and becomes the pattern every later table copies, so
each one is cheap now and expensive in Phase 3.

Four questions needed answers.

**1. What type are primary keys?** The platform hands job ids back to callers
who poll them, and issue keys to the MCP server. A sequential integer id tells
an unrelated user how many jobs the platform has run and is trivially
guessable; a UUID is neither. Against that, a UUID is 16 bytes rather than 8,
is random, and therefore scatters index inserts across the whole B-tree
instead of appending at one end.

**2. How are enumerated values stored?** Postgres has a real `ENUM` type.
SQLAlchemy can also map a Python enum onto `VARCHAR` with a `CHECK`.

**3. How is `updated_at` maintained?** Either the ORM sets it, or a database
trigger does.

**4. Who names constraints?** Postgres will invent a name if nobody supplies
one.

## Decision

**UUID primary keys, except `audit_logs`.**

`users`, `user_project_access`, `jira_issues` and `jobs` use
`uuid` with `server_default=gen_random_uuid()` and a Python-side
`default=uuid.uuid4`, so the ORM knows the id before the INSERT and a row
inserted by hand still gets one. `gen_random_uuid()` is built into PostgreSQL
13+, so no extension is needed.

`audit_logs` uses `bigint GENERATED BY DEFAULT AS IDENTITY`. It is append-only
and almost always read in time order, so a monotonic key keeps inserts at the
right-hand edge of the index. Nothing outside the system ever quotes an audit
id, so there is no enumeration exposure to trade against. Identity rather than
`BIGSERIAL`: identity is standard SQL and the sequence belongs to the column,
so there is no separately-owned object to grant on or forget during a restore.

**Enums are `VARCHAR` with a `CHECK` constraint,** via
`app.models.base.enum_column`, which sets `native_enum=False` **and
`create_constraint=True`**.

Both flags are required. `create_constraint` has defaulted to `False` since
SQLAlchemy 1.4, so `native_enum=False` on its own produces a bare `VARCHAR`
that accepts any string whatsoever. The Step 5 verification inserted
`role='superuser'` successfully before this was corrected.

`values_callable` makes the stored text the member value (`qa_engineer`), not
the member name (`QA_ENGINEER`), which is SQLAlchemy's default.

**`updated_at` is maintained by the ORM,** through SQLAlchemy's `onupdate`, not
by a trigger.

**Constraint names come from a naming convention** on `Base.metadata`:
`pk_`, `uq_`, `ck_`, `fk_`, `ix_` prefixes with the table and column names
appended.

## Alternatives considered

**`bigint identity` everywhere.** Half the storage, better index locality, and
easier to read in a terminal. Rejected for the externally-visible tables
because job ids are handed to callers: a caller who receives job 4,181 learns
the platform's total throughput, and can try 4,180. For a purely internal table
such as `audit_logs` this reasoning does not apply, which is why that table
does use one. Mixing the two types is a real cost — a reader has to notice —
and the module docstring on `AuditLog` states the reason at the site.

**UUIDv7 for every key.** Time-ordered, so it gets UUID's unguessability and
bigint's index locality. Genuinely the best answer on paper. Rejected for now
because Postgres 17 has no built-in generator (`uuidv7()` arrives in Postgres
18), so it would mean a hand-written PL/pgSQL function or generating ids only
in Python, giving up the `server_default` that lets `psql` and data migrations
work. Worth revisiting when the deployment target is Postgres 18.

**Native Postgres `ENUM`.** Smaller on disk, self-documenting in `\dT`, and
rejects bad values without a separate constraint. Rejected because changing one
is painful in a way that shows up at the worst time: `ALTER TYPE ... ADD VALUE`
cannot run inside a transaction block on PostgreSQL before 12, and even on
newer versions the new value cannot be used in the same transaction that adds
it. Removing or renaming a value means creating a new type, rewriting every
column that uses it, and dropping the old one. This schema has five enum
columns and later phases will add values to `job_type`; `VARCHAR` plus `CHECK`
makes that a one-line migration.

**A plain `VARCHAR` with validation only in Pydantic.** Simplest, and the
application does validate. Rejected: the database is also written by
migrations, by `psql`, and in Phase 4 by a worker process. A constraint that
only one of four writers enforces is not a constraint.

**A trigger for `updated_at`.** Correct in every case, including raw SQL and
bulk updates. Rejected for Phase 1 because it is DDL that `--autogenerate`
does not manage: the trigger would live only in a hand-written migration, and
every later `alembic check` would be silent about it, which is the same class
of invisible drift that the `create_constraint` bug above belongs to. The cost
is that `updated_at` is stale after a raw `UPDATE`; that caveat is on the
`TimestampMixin` docstring and in the Step 5 known issues. If anything starts
updating these tables outside the ORM, add the trigger.

**Letting Postgres name constraints.** Rejected outright. Autogenerate emits
`op.create_unique_constraint(None, ...)` for an unnamed constraint, and a later
migration that needs to drop it has nothing to reference — the downgrade cannot
even be written. The convention must be set before the first table exists,
because changing it later renames every constraint in the database.

## Consequences

- Every table except `audit_logs` has a 16-byte random primary key. Index
  inserts scatter. At this platform's write volume — issues cached on demand,
  jobs created by humans — that is not measurable, but it would be at a
  million rows a day.
- A reader must notice that `audit_logs` differs. Flagged in its docstring.
- Adding an enum value is a migration, not a code-only change. That is the
  intended trade.
- **`alembic check` does not compare CHECK constraints.** It reported "no new
  upgrade operations" both before and after the `create_constraint` fix. A
  passing `alembic check` therefore does not mean the schema matches the
  models. Anyone changing a `CHECK` must verify against the catalog by hand;
  the Step 5 log has the query.
- `updated_at` lies after a raw SQL `UPDATE`. Known and documented.
- Constraint names are predictable, so a migration can always name what it
  drops, and the Step 5 verification can assert that every constraint in the
  database follows the convention.
