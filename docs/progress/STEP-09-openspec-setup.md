## How it works

### The finding that shaped the step

The brief says "OpenSpec BRD generation", which reads like OpenSpec is a
library that writes requirements. It is not. `@fission-ai/openspec` 1.16.1 is a
workflow for AI coding agents: a developer types `/opsx:propose`, the **agent**
writes the spec files, and the CLI scaffolds, validates and archives them. Its
commands are `change`, `spec`, `show`, `validate`, `workset`, `config`,
`doctor`, `store`. Its dependencies are `commander`, `@inquirer/prompts`,
`chalk`, `ora`, `yaml`, `zod` — no LLM client anywhere.

So OpenSpec cannot turn `SCRUM-1` into requirements. A model does that. What
OpenSpec contributes is the format and a real validator.

### The two roles, kept apart

```
openspec/                 <- us, planning this platform. Not read at runtime.
  specs/                     the agreed spec per capability
  changes/<name>/            proposal.md, specs/, design.md, tasks.md

a generated BRD           <- product output, one per Jira issue.
                             Uses OpenSpec's markdown conventions:
                               ## ADDED Requirements
                               ### Requirement: ...
                               #### Scenario: ...
                               - **WHEN** ... - **THEN** ...
                             Stored where Step 11 decides. Not in openspec/.
```

The format is reused because named WHEN/THEN scenarios in a fixed shape are
good input for DSPy in Phase 3. Nothing deeper than that.

### Why the CLI stays out of the request path

Running it inside the API container would mean Node.js 22 beside Python 3.12 —
a second runtime and its patch stream — to shell out to an interactive CLI from
a web request, with telemetry on by default. And it would still not generate
anything. `openspec validate --all` belongs in CI and the worker, where a
structural check on output belongs.

## How to run / verify

```bash
openspec --version          # 1.16.1
openspec list               # No active changes found.
openspec validate --all     # No items found to validate.  (exit 0)
```

All three are correct for a freshly initialised project with no changes yet.

Note that bare `openspec validate` **fails without a terminal**:

```
Nothing to validate. Try one of:
  openspec validate --all
```

which is why the README and any future CI step use `--all`.

## Decisions and trade-offs

**The CLI is a development dependency, not a runtime one.** Full reasoning in
ADR-019, including the option that was rejected: Node in the API image with a
subprocess per request. The honest cost of the decision we took is that
`openspec validate` does not run automatically on generated output yet, because
there is no CI.

**`claude-sonnet-5-5` as the default, as configuration.** ADR-020. Opus is a
better writer of requirements from a thin ticket; Sonnet is the right default
for a phase whose prompt will be rewritten twenty times. `LLM_MODEL` makes it
one line.

**Telemetry disabled.** `openspec config set telemetry.enabled false`. It is
global developer config, so it is per-machine and nothing in the repository can
enforce it — recorded in the README and in ADR-019's consequences.

**Committing the 24 generated instruction files.** They are the shared
workflow and hold no secrets. The alternative — gitignoring them and having
each developer run `openspec init` — produces a different workflow per machine
depending on CLI version.

**`openspec/config.yaml` holds constraints, not documentation.** The temptation
is to paste the README in. The config explicitly asks for what an agent cannot
infer by reading the code, so it holds the gatekeeper rule, the documentation
rule and the no-SQLite rule, and nothing that `ls` would answer.

## Security notes

- **Telemetry was on by default and is now off.** It reports command names and
  version, not arguments, paths or content. Low severity, but an internal
  platform should not report its activity to a third party by inheritance.
- **`npm install -g` executed third-party code.** 57 packages. The version is
  pinned to `1.16.1` rather than `latest` so the same tree is reproducible, and
  the package is MIT with a public repository. No lockfile covers it, because
  it is global; that is a real gap compared to `uv.lock` for Python.
- **ADR-020 records a new data-handling fact**: generating a BRD sends Jira
  ticket text to Anthropic. Nothing sends anything yet — no key is configured
  and no client exists — but the decision is written down before the code, so
  whoever reviews this platform before it reads a real tenant's tickets sees it
  rather than discovers it.
- **No secret was added in this step.** `ANTHROPIC_API_KEY` is described in
  ADR-020 and is not yet in `.env.example`; Step 10 adds it, together with the
  validator and the placeholder marker that make the startup warning cover it.
- **The generated instruction files were scanned** for credential-shaped
  content before being committed, and contain none.

## Known issues / TODO

- **No CI, so `openspec validate --all` never runs on its own.** This is now
  the second reason to add a workflow; ADR-018 was the first. The suite needs
  nothing, so it is about ten lines.
- **`openspec update` after a CLI upgrade is manual** and will be forgotten.
  The 24 committed files would then be stale relative to the installed CLI.
- **Nothing validates generated BRDs yet** — there are none. Step 11 writes the
  first, and Step 11 is also where the storage location is decided, which
  ADR-019 deliberately left open.
- **The word "spec" is overloaded** three ways in this repository: an OpenSpec
  change, a generated BRD, and a Pydantic schema. Only a README paragraph
  separates them.
- **`openspec/` is empty.** Phases 3 to 5 are meant to be proposed through it,
  and until one of them is, the workflow is set up but unproven.
