# Step 12: The brd module — a Jira issue becomes a stored document

Date: 2026-11-09
Phase: 2

## Goal

Wire `app/llm/` to the rest of the platform: a table for generated documents, a
module that decides who may generate one, and two endpoints. After this step
the feature exists end to end except for the MCP tool and a live model call.

## What was done

| Path | Why |
| --- | --- |
| `docs/decisions/ADR-024-…` | Where a generated document lives: the database row, not a file. ADR-019 left it open. |
| `app/models/brd_document.py` | One row per generation **attempt**, with eight CHECK constraints making the impossible states unreachable. |
| `migrations/versions/…_brd_documents.py` | The table. Autogenerated, then verified by trying to violate every constraint. |

| `app/modules/brd/service.py` | The policy: six gates, in an order that is the module's security property. |
| `app/modules/brd/router.py` | `POST /api/v1/brd` and `GET /api/v1/brd/{issue_key}`. |
| `app/main.py` | Router registered. |
| `tests/unit/test_brd_service.py` | 23 tests about order and refusal, with every collaborator stubbed. |
| `docs/api.md` | Both endpoints, including why the 404 comes before the 503. |

## How it works

### The gates, and why one is delegated

```
1. shape            IssueKeyPath rejects a malformed key
2-4. access         delegated to jira.service.get_issue:
                      registered -> active -> project grant -> cache/Jira
5. configured       is there a model to call at all
6. existing         return the current document unless regenerate=true
--- only now is anything spent ---
7. open a pending row, commit it
8. call the model
9. validate, then store or record the failure
```

Gates 2 to 4 are **not reimplemented**. Generating needs the issue, and getting
the issue already means "registered, active, holds a grant, cache or Jira" —
four checks in a fixed order that exist in one place. A second copy here would
be a second place for that order to be wrong, and the order is the part that
matters: **nothing reaches a model on behalf of a caller who was going to be
refused.**

Gate 5 sits **before** gate 6 deliberately. The other way round, an
unconfigured server would appear to work for exactly those issues that happen
to have a document already.

### Nothing partial is ever stored

Three ways a generation fails after the model has been paid for, and all three
produce a `failed` row rather than a document:

- **The provider failed** — timeout, rate limit, 5xx. Recorded with the error
  code as the reason.
- **The reply was cut off** (`finish_reason == "length"`). This is the subtle
  one: a truncated requirements document looks *complete*, not short — four
  well-formed requirements instead of six — so it would pass validation. It is
  caught before validation and recorded as `truncated`.
- **The reply was not a usable document.** Recorded as `invalid_format`.

Token usage is kept on a failure. An unusable reply was still charged for, and
a cost report counting only successes understates spend exactly when something
is going wrong.

### The pending row exists before the model is called

Written and committed first, so a generation that never returns leaves a
visible row instead of nothing. The partial index
`ix_brd_documents_pending` exists to find them.

### What the database refuses

Eight CHECK constraints, so the impossible states are unreachable regardless of
any bug in the service:

| Constraint | Makes this impossible |
| --- | --- |
| `document_status_has_markdown` | A `ready` row with no document. |
| `terminal_status_has_finished_at` | A finished row with no finish time, or a pending one with one. |
| `failed_status_has_reason` | A failure nobody can explain. |
| `brd_status` | An invented status such as `approved`. |
| `issue_key_format` | A row for `not-a-key`. |
| `actor_email_lowercase` | One person appearing as two actors (ADR-017). |
| `requirement_count_non_negative`, `scenario_count_non_negative` | Negative counts. |

Each one was verified by trying to break it, because Step 5 established that
`alembic check` does not compare CHECK constraints.

## How to run / verify

```bash
uv run pytest -q             # 591 passed
uv run ruff check .          # All checks passed!
uv run alembic upgrade head
```

Against the running stack, with generation **not** configured, which is the
state that proves the gate order:

```bash
T=$(grep '^INTERNAL_API_TOKEN=' .env | cut -d= -f2-)
H=(-H "Authorization: Bearer $T" -H "X-Actor-Email: you@example.com" -H "Content-Type: application/json")

# A project you can see: refused for the right reason, naming what to set.
curl -s "${H[@]}" -X POST -d '{"issue_key":"SCRUM-1"}' http://127.0.0.1:8000/api/v1/brd
# 503 service_unavailable
#   "Document generation is not configured on this server. Ask an
#    administrator to set LLM_MODEL and LLM_API_KEY."

# A project you cannot see: 404, NOT 503. Access is decided first, so an
# unauthorised caller learns nothing about whether the feature exists.
curl -s -o /dev/null -w "%{http_code}\n" "${H[@]}" \
     -X POST -d '{"issue_key":"ABC-1"}' http://127.0.0.1:8000/api/v1/brd
# 404

# An unknown field.
curl -s -o /dev/null -w "%{http_code}\n" "${H[@]}" \
     -X POST -d '{"issue_key":"SCRUM-1","regenrate":true}' http://127.0.0.1:8000/api/v1/brd
# 422
```

## Decisions and trade-offs

**A document is a row, not a file.** ADR-024 in full. The Step 1 scaffold wanted
files so BRDs could be reviewed in a pull request; that would mean the API
holding a git credential and pushing commits from a web request. The row has to
exist anyway, because Phase 3 generates tests from it.

**Regeneration appends; nothing is overwritten.** A BRD written against a ticket
as it was last Tuesday is evidence of what was agreed then. "The current BRD" is
therefore a query — the newest `ready` or `needs_info` row — rather than a flag
two writers could both set. The cost: the table grows and nothing prunes it.

**`needs_info` is a success, not a failure.** When a ticket says too little the
prompt asks for open questions instead of invented requirements, and that reply
is stored as a document. It is recorded under its own status because nothing can
be tested from it, and Phase 3 must not try.

**200, not 201, on generate.** The common case is reuse. A status code that
depended on whether a document was created would make every caller branch on
it; `reused_existing` says which happened.

**`regenerate` defaults to false.** Generating costs money and rate limit. The
default is the cheap, usually-correct answer.

**Delegating the access gates costs a wasted Jira read on a pure document read.**
`GET /api/v1/brd/{issue_key}` runs the full issue read in order to reuse the
gate order, which may hit Jira for an issue whose document is already stored.
The alternative was a second copy of the four-gate sequence, and that sequence
is the single thing in this codebase least worth duplicating.

## Security notes

- **The order of gates is the security property, and it is now asserted.** A
  test makes the delegated gate raise and then checks the model was never
  called and no row was opened. The real risk it guards is not a wasted call:
  it is a refused caller's ticket text being sent to a third-party provider.
- **The 404 precedes the 503.** Verified live. An unauthorised caller cannot
  use this endpoint to discover whether generation is configured, which is a
  small inference but a free one to deny.
- **A refused generation is audited under its own action.** Found by a live
  call during this step: the delegated gate audited `jira_issue.read`, which is
  true but left "who tried to generate a document for ABC-1" unanswerable. One
  refusal now writes two rows, which is accurate — the generation was refused,
  and the read it required was refused.
- **The model's own words never reach `failure_reason`.** It takes a short code
  from a fixed set, truncated to 64 characters. The reply is untrusted text
  (ADR-023) and that column is read by people and by SQL. A test asserts a
  reply containing `IGNORE PREVIOUS INSTRUCTIONS` is recorded as
  `invalid_format`.
- **`actor_email` is lowercased by a CHECK constraint**, not by convention, so
  ADR-017's "one person is one actor" holds for this table even for a row
  written by something that forgets.
- **A generated document is now in `pg_dump` output.** ADR-009 limited what the
  *cache* stores; this is a deliberate exception for a document the platform
  authored, and it is why ADR-024 flags the absence of a retention policy.
- **No new secret.** This step adds no credential.

## Known issues / TODO

- **No live generation has happened.** `LLM_MODEL` is unset because
  `models.github.ai` is unreachable from the development sandbox, so the
  catalogue could not be listed from here. The model name must be exact, and
  guessing one into `.env` is how you get a 404 that reads like a broken
  endpoint.
- **No MCP tool yet**, so Copilot Chat and Claude Code cannot generate a
  document. That is Step 13: `generate_brd(issue_key)` plus its fail-closed
  audit tests.
- **Nothing checks that a document is about the right issue.** A model can
  return a well-formed BRD describing something else. Detecting that needs a
  comparison against the issue and it is not obvious how to do it without being
  brittle.
- **No retention policy.** A prompt-tuning session on one ticket produces a row
  per attempt, and nothing prunes them.
- **`pending` rows are never cleaned up.** The partial index finds them; no job
  closes them. A generation killed mid-flight leaves a row that is pending
  forever.
- **`GET /api/v1/brd/{issue_key}` can hit Jira.** See the trade-off above.
- **Still no integration tests.** The constraint checks in this log were run by
  hand, and the stub repository in the unit tests can drift from the real one.
