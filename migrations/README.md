# migrations

Alembic migration environment. The configuration lives in `alembic.ini` at the
project root; this folder holds `env.py`, the revision template, and the
revisions themselves.

## Everyday commands

Run these from the project root, with `.env` present and Postgres up.

Apply everything:

```
uv run alembic upgrade head
```

Show the current revision:

```
uv run alembic current
```

Create a revision from model changes:

```
uv run alembic revision --autogenerate -m "short description"
```

Produce SQL for a DBA to review instead of applying it, which is how a
production change should go out:

```
uv run alembic upgrade head --sql
```

Roll back one revision:

```
uv run alembic downgrade -1
```

## Rules

- Every schema change ships as a migration. No manual DDL against any shared
  database.
- **Review the autogenerated revision by hand before committing it.** Replace
  the generated docstring with one that says what the revision does and what
  you changed during review.
- **`alembic check` is not a safety net.** It compares tables, columns and
  indexes. It does **not** compare `CHECK` constraints at all, and it compares
  types and server defaults only because `env.py` sets `compare_type` and
  `compare_server_default`. A `CHECK` you add to a model will never appear in
  an autogenerate diff — write that migration by hand and confirm it against
  `pg_constraint`. This is not hypothetical; see the Step 5 log.
- Autogenerate also misses: table and column renames (it sees a drop plus an
  add, which loses the data), trigger and function changes, and anything in a
  schema other than `public`.
- Test `downgrade()` before you commit. Run `upgrade head`, then
  `downgrade -1`, then `upgrade head` again.
- A revision that changes data as well as schema needs the data step written
  explicitly. Autogenerate only ever writes DDL.
- No credentials here. The URL comes from `app.core.config` via `env.py`;
  `sqlalchemy.url` in `alembic.ini` is deliberately empty.

## Why `env.py` uses a blocking engine

Migrations are a serial batch job, so async buys nothing and costs an
event-loop wrapper around every revision. The application itself is async. See
[ADR-006](../docs/decisions/ADR-006-async-sqlalchemy.md).

## Why `env.py` imports `app.models`

Importing that package is what registers every model on `Base.metadata`. A
model in a module nobody imports is invisible to `--autogenerate`, and the
symptom is a revision that silently drops the table. Add every new model module
to `app/models/__init__.py`.
